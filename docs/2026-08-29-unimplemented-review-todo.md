## 0. 체계

이 문서는 자기완결이다. 아래에 정의하지 않은 표기는 본문에 쓰지 않는다.

**작업 ID** — `<단계>.T<번호>`. 문서가 개정돼도 같은 작업을 가리킨다. 번호는 재사용하지
않는다. 지운 작업은 번호를 남기고 `(폐기)` 를 붙인다.

**상태 표기 두 벌**

| 대상 | 표기 |
|:--|:--|
| 작업 | `☐` 미착수 · `▶` 진행 · `☑` 완료 |
| 단계 | `🔒` 잠김 · `🔓` 열림 · `🔏` 봉인 |

🔒 **잠긴 단계의 작업은 시작하지 않는다.** 선행 단계가 봉인되기 전에는 그 단계의 게이트
실행 자체가 거부되므로(R1), 작업을 해 두어도 통과를 기록할 방법이 없다.

**작업 하나의 모양**

```
### <작업 상태> <작업 ID> — <제목>
    선행:     이 작업 앞에 끝나 있어야 하는 작업 ID, 없으면 —
    산출:     이 작업이 만들거나 바꾸는 경로
    되돌리기: 이 작업을 취소하는 단위 (커밋 하나 = 작업 하나)

    【작업】   번호 하나 = 커밋 하나
    【테스트】 TC 목록
    【통과】   체크박스. 전부 기계 판정
```

**테스트케이스 규칙** — `TC-<작업 ID>.<a|b|c…>`, 세 줄로 적는다.

```
TC-<작업 ID>.a  <이름 — 무엇을 확인하는지>
  단언:  <기계가 판정하는 조건>
  검출:  <이 테스트가 없으면 무엇이 어떻게 깨져서 무엇을 놓치나>
```

검출줄을 못 쓰면 그 테스트는 쓰지 않는다. 「X 가 안 되는 것」처럼 이름을 되풀이하는
검출줄은 검출줄이 아니다.

**GATE 와 봉인**

장치는 `scripts/gate.mjs` 다. `P0.T1` 이 만든다. 계약은 바로 아래에 있다.
봉인 파일은 `gates/<단계>.json` — **추적되는 위치**여야 한다. 봉인은 증거이고, 무시되는
디렉터리에 있는 증거는 증거가 아니다.

| 규칙 | 동작 |
|:--|:--|
| **R1 순서** | 선행 단계의 봉인이 없으면 이 단계의 검사 실행 자체를 거부한다 |
| **R2 최신성** | 봉인 **파일**을 마지막으로 건드린 커밋이 `HEAD` 의 조상이 아니면 그 봉인을 **무효**로 표시한다 — 되돌리면 자동으로 풀리고, 스쿼시·리베이스는 견딘다. `head` 는 출처다 |
| **R3 재검** | `--seal` 은 이전 결과를 읽지 않는다. 검사를 처음부터 다시 돌린다 |

**게이트 장치 계약** — `P0.T1` 이 이 여섯을 만든다. 이름은 `scripts/gate.mjs` 로 고정한다.

```
node scripts/gate.mjs <단계>            봉인 전이면 검사를 돌려 표로 낸다. 실패 시 종료코드 ≠ 0
                                        이미 봉인됐으면 **봉인을 읽는다** — 창이 지나간 단계를
                                        다시 재면 나오는 빨강은 회귀가 아니다
node scripts/gate.mjs <단계> --recheck   봉인됐어도 지금 다시 잰다
node scripts/gate.mjs <단계> --seal     검사를 다시 돌려 전부 초록이면 봉인 파일을 쓴다
node scripts/gate.mjs <단계> --explain  실패한 검사의 측정값과 상한을 뱉는다
node scripts/gate.mjs <단계> --seal --waived "<사유>"
                                        하지 않기로 한 단계를 봉인한다. 사유 없으면 거부
node scripts/gate.mjs --status          단계별 잠김·열림·봉인·무효를 「진행 현황」과 같은 열로
node scripts/gate.mjs --assert-order [--base <커밋>]
                                        CI 용. 봉인 안 된 단계의 산출 경로에 변경이 있으면 실패.
                                        기준을 못 찾으면 통과하지 않는다 — 「비교하지 않았다」는
                                        「문제가 없다」가 아니다
```

봉인 파일 `gates/<단계>.json` 의 모양:

```json
{ "phase": "P0", "sealed": true, "head": "<커밋 SHA>", "at": "<ISO>",
  "waived": false, "reason": null,
  "checks": [ { "id": "G-P0.3", "ok": true, "measured": 1, "limit": 1 } ] }
```

검사 정의는 **데이터**다 — 파일 상단의 `GATES` 객체 하나. 검사를 더하는 일이 코드 분기를
더하는 일이 되면, 검사를 더하지 않게 된다.

```js
const GATES = {
  P1: { needs: ['P0'], checks: [
    { id: 'G-P1.1', how: 'grep', pattern: 'only real provider', in: 'README.md', limit: 0 },
    { id: 'G-P1.3', how: 'grep', pattern: 'RFC 2136', in: 'README.md',
      between: ['^## Status & limitations', '^## License'], min: 1 },
    { id: 'G-P1.7', how: 'diff-empty', paths: ['src/', 'test/'], since: 'seal:P0' },
    { id: 'G-P1.9', how: 'test', cmd: 'node --test test/infrastructure/schema-surface.test.ts' },
    { id: 'G-P1.11', how: 'json', file: 'gates/P0.json', path: 'checks[id=G-P0.6].measured', op: '<=' },
  ]},
};
```

`how` 여섯 — `lines`(파일 줄 수) · `grep`(등장 수, `between` 으로 절 스코프) ·
`test`(테스트 파일 하나) · `cmd`(종료코드) · `diff-empty`(경로에 변경 없음) ·
`json`(봉인 값과 비교). 이 여섯이면 계획서의 숫자 전부가 검사로 옮겨진다.

썩은 경로가 그 두 문장에도 똑같이 열려 있기 때문이다.

## 선행 관계

```
P0 ──▶ P1 ──▶ P2
기준선   문장    검사
장치     정정    묶기
```

**직렬이다. 동시 진행 상한 1.** 병렬 가능한 곳이 없는 이유는 셋이 같은 파일을 만지기
때문이 아니라, **각 단계가 앞 단계의 산출을 측정 대상으로 쓰기** 때문이다 — P1 의 통과는
P0 이 기록한 기준선에 대한 델타이고, P2 의 검사는 P1 이 만든 문장을 대상으로 한다.

# P1 — §R1 정정 🔏 (P0 봉인됨)

**브랜치** `docs/r1-provider-adapter-claim`

§R1 의 판정은 「거짓」이고, 정정 방향은 「없다 → 있다」가 아니라 **축 바꾸기**다. 계획서
§R1 「무엇을 쓸 것인가」가 그 축을 정해 두었다.

### ☑ P1.T1 — 두 README 의 한계 절을 외부/내부로 가른다
    선행:     P0 봉인
    산출:     `README.md`, `README.ko.md`
    되돌리기: 커밋 하나. 문장만 바뀌므로 되돌려도 코드 영향 0

【작업】

1. 한 커밋으로 두 언어를 함께 바꾼다. **언어별로 쪼개지 않는다** — 두 문서가 서로 다른
   것을 말하는 상태가 커밋 하나만큼이라도 존재하면, 그것이 §R1 이 생긴 상태다.

## 막혔을 때

**게이트가 빨간데 원인을 모른다** — `--explain` 을 먼저 본다. 측정값과 상한을 함께
내므로, 「어느 검사가」가 아니라 「얼마만큼」이 나온다. `grep` 검사가 0 을 내면 패턴이
대상을 못 잡는 쪽을 먼저 의심한다(TC-P0.T2.b 가 그 사고다).

**봉인 후에 회귀했다** — 되돌리지 않는다. 봉인의 `head` 가 조상이 아니게 되면 R2 가
자동으로 무효로 표시하므로, 회귀를 되돌리면 봉인이 스스로 풀린다. 손으로 봉인 파일을
지우는 것은 그 자동성을 못 믿게 만든다.

**이동인지 변경인지 모른다** — 이 실행판에 순수 이동은 없다. P1 은 문장 교체(행동
변경 아님, 소스 diff 0 으로 증명), P2 는 검사 추가(신규)다. 판단이 필요한 상태가
생기면 그 작업은 쪼개지지 않은 것이다.

**위험한 단계 중간에 이탈해야 한다** — P1 이 유일한 위험 구간이고, 위험은 두 README 가
서로 다른 것을 말하는 상태다. P1.T1 은 **한 커밋으로 두 언어를 함께** 바꾸므로 그
상태가 커밋 사이에 존재하지 않는다. 이탈은 커밋 경계에서 하면 안전하다.

**일정이 부족하다** — P0 을 건너뛰지 않는다. P1 만 하고 P2 를 미루는 것은 가능하고,
그 경우 P2 를 `--waived "P1 만 반영, 재발 방지는 다음 사이클"` 로 봉인한다. 사유 없는
면제는 장치가 거부한다. **P0 을 면제하는 경로는 없다** — 장치가 없으면 면제조차 기록할
곳이 없다.

**② 기준선 봉인은 다시 뜰 수 없다.** `G-P0.3`·`4`·`5` 는 「낡은 문장이 아직 있다」를 재므로,

그래서 **순서를 한 번 바로잡아야 했다.** P0 산출물의 정정이 P1.T1 뒤에 커밋돼 있었고, 그

🔑 **그리고 이것은 P0 만의 성질이 아니었다.** P2 가 `test/` 에 파일을 더한 뒤 `gate P1` 을
다시 돌리면 `G-P1.7`(소스 무변경, `since: seal:P0`)이 빨개진다 — P1 의 창에서는 참이었고
지금도 그 창에서는 참인데, 창이 지나갔다. 일반화하면:

> **봉인된 단계의 검사는 그 단계의 창 안에서만 다시 돌 수 있다.** 창이 지나간 뒤의 답은
> 봉인에 있고, `--status` 가 그것을 읽는다. `gate <단계>` 를 나중에 돌려 빨간 것을 회귀로
> 읽으면 안 된다 — 그 명령은 「지금 이 단계를 통과할 수 있나」를 묻고, 지나간 단계에 그
> 질문은 뜻이 없다.

계획이 이 구별을 적지 않았다. 장치는 이미 옳게 동작한다(`--status` 는 봉인을 읽고 재검하지
않는다). 적히지 않은 것은 **읽는 사람이 무엇을 회귀로 봐야 하는가**였다.

**③ R2 를 손으로 검증할 기회가 있었다.** 커밋을 `--amend` 하면서 봉인의 `head` 가 이력에서
사라졌고, `--status` 가 즉시 **무효**로 표시하며 P1 을 다시 잠갔다. 규칙이 의도대로 걸렸다 —
봉인을 지우지 않아도 되돌리면 스스로 풀린다.

🔴 **그런데 그 규칙이 틀렸다. 머지되고 나서 알았다.** 이 저장소는 모든 PR 을 **스쿼시**로
머지한다(`#8`~`#21` 전부 커밋 하나). 스쿼시는 원래 커밋을 이력에서 지우므로, `head` 조상
관계로 판정하면 **머지되는 순간 세 봉인이 한꺼번에 무효가 된다** — 일이 정상적으로 landed 한
바로 그때. main 에서 실제로 그렇게 됐고, `--status` 가 셋 다 무효라고 답했다.

기준을 **봉인 파일이 지금 이력에 있는가**로 바꿨다: 그 파일을 마지막으로 건드린 커밋이 `HEAD`
의 조상인가. 단계를 되돌리면 봉인 파일도 함께 되돌려지므로(같은 커밋에 들어 있다) 자동으로
풀리는 성질은 남고, 스쿼시·리베이스는 견딘다. `head` 는 판정에서 **출처**로 내려앉았다.

📌 「되돌리면 풀린다」를 커밋 sha 로 구현한 것이 원인이다. sha 는 내용이 아니라 **이력의
모양**을 가리키고, 이 저장소의 이력 모양은 머지마다 바뀐다. 규칙을 쓸 때 그 저장소가 어떻게
머지하는지를 보지 않았다.

**④ 같은 음성 대조가 환경 때문에 세 번 틀렸다.** `TC-P0.T1.g` 가 `--assert-order` 를
검사하는데, 셋 다 **주변 git 상태를 단언**한 결과였다:

| 판 | 무엇에 기댔나 | 어디서 틀렸나 |
|:--|:--|:--|
| 1차 | 기준을 안 넘겨 `merge-base(origin/main, HEAD)` 폴백에 맡김 | PR CI — `origin/main` 이 없어 폴백이 조용히 0 을 냈다 |
| 2차 | `HEAD~1` | PR CI — `fetch-depth: 1` 에는 부모가 없다 |
| 3차 | `base: ""` 로 「기준 없음」을 만들려 함 | **main CI** — `origin/main` 이 **있어서** 폴백이 성공했다 |

폴백은 정의상 환경에 달렸으므로 그 경로를 단언하면 그 환경에서만 맞는다. 4차 판은
「지정하지 않음」과 「명시적으로 없음」을 갈라(`base: null`) 폴백을 아예 타지 않고, 검증은
`git clone --depth 1` 로 두 조건을 **둘 다** 재현해서 했다.

🔑 **셋 다 「로컬에서 초록이니 됐다」로 밀었다가 다른 환경에서 걸렸다.** 그리고 세 번째는
머지 뒤 main 에서만 걸려서, PR 이 초록인데 main 이 빨간 상태를 만들었다.

### 봉인된 단계를 그냥 돌리면

`gate <단계>` 는 이제 **봉인을 읽는다.** 창이 지나간 단계를 다시 재면 빨강이 나오는데 그
빨강은 회귀가 아니라 질문이 틀린 것이고, 읽는 사람이 그 구별을 이 문서에서 찾아야 했다.
지금은 장치가 말한다 — `--recheck` 가 그래도 지금 재라는 뜻이다.

⚠️ `--seal` 은 그 편의를 타지 않는다(`recheck: true` 를 명시로 넘긴다). 타면 옛 초록으로
다시 봉인되고, 그것이 R3 가 막으려는 바로 그것이다. `TC-P0.T1.c` 가 그 줄이 없을 때 빨개진다.

⚠️ **§0 의 R2 문구가 `origin/main` 이라고 적혀 있었다.** `TC-P0.T1.b` 는 처음부터 `HEAD` 를
단언했으므로 산문만 틀렸다. 기능 브랜치에서 `origin/main` 기준이면 갓 찍은 봉인이 전부
무효가 되어 쓸 수 없다. 문구를 `HEAD` 로 고쳤다.

**⑤ 금지 표식의 자기 매치.** `G-P2.7` 이 「`GATE-TEMP` 가 남아 있지 않다」를 검사하는데, 그
표식을 정의하는 파일·실행판·음성 대조 셋이 그것을 인용한다. **이름으로** 면제했다 —
규칙(「검사 파일은 모두 면제」)으로 면제하면 다음 면제가 조용히 늘고, 그러면 금지가 아니라
권고가 된다. `TC-P0.T1.h` 가 면제가 이름으로만 걸리는지 확인한다.

### 남은 하나

`--assert-order` 를 CI 에 배선하는 일. **선행 조건은 해소됐고, 지금 넣지 않는 이유는 처음
적었던 것과 다르다.**

처음 적을 때의 이유는 이랬다: `deployment-gate` 잡은 `fetch-depth` 가 얕아 `origin/main` 이
없고, 그러면 비교 기준이 없어 이 명령이 **조용히 통과한다** — 얕은 체크아웃에서 vacuous 하게
초록인 검사를 CI 에 넣는 것은 넣지 않는 것보다 나쁘다.

⚠️ **그 문장이 가리킨 결함이 검사 자신에게 있었고, 실행 중에 고쳤다.** 이제 기준을 못 찾으면
비영으로 끝나고(「비교하지 않았다」와 「문제가 없다」는 같은 답이 아니다), CLI 가
`--assert-order --base <커밋>` 을 받는다. 그래서 배선은 기술적으로 가능하다.

🔑 **그런데 지금은 볼 대상이 없다.** 이 검사는 **봉인되지 않은** 단계의 산출이 바뀌었는지
묻는다. 세 단계가 다 봉인된 지금은 어떤 편집도 걸리지 않으므로 영구 초록이다 — 그리고 영구
초록인 검사를 CI 에 두면, 다음 사람은 그것이 무언가를 지키고 있다고 읽는다. 이 실행판이 P2
에서 배운 것이 정확히 그것이다: 초록은 「통과」와 「측정하지 않음」을 구별하지 못한다.

**그러니 다음 실행판이 `GATES` 에 새 단계를 붙이는 날 함께 넣는다.** 그때는 볼 대상이 있고,
base 를 무엇으로 줄지도 그 CI 잡이 정해진 뒤에 답할 수 있다.

📌 이 항목이 세 번 다시 쓰였다 — 못 한다 → 선행 조건이 해소됐다 → 할 수 있지만 지금은 쓸모가
없다. 남겨 두는 항목의 **이유**는 그 항목만큼 자주 바뀐다.
