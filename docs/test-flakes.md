# 간헐 실패 기록

`pnpm test` 가 **한 번** 빨개졌고 다시 나지 않은 관찰을 여기 적는다. 목적은 하나다 —
**재발이 첫 목격이 되지 않게 하는 것.**

기록되지 않은 간헐은 매번 처음 보는 일이 된다. 그리고 이 저장소는 그 대가를 이미 한 번
치렀다: `AGENTS.md` 가 「러너가 느려서」로 넘겼으면 같은 코드 세 줄에 붙어 있던 **조용한
쪽**을 못 봤을 거라고 적어 두었다. 시끄러운 쪽이 눈에 띈 것뿐이었다.

> 📋 **여기 적는 것과 적지 않는 것.** 재현되지 않은 관찰만 적는다. 재현되면 그것은 결함이고
> 결함은 고치거나 `docs/todo.md` 로 간다. 고쳐진 뒤에는 이 파일에서 지우지 않고 **닫힌
> 것으로 남긴다** — 다음에 비슷한 증상을 보는 사람이 무엇이 배제됐는지 알아야 한다.

---

## 열림 · 2026-08-31 (2차) · 같은 증상, 여전히 이름 없음

**증상.** `pnpm test` 가 `1096 tests / 1092 pass / 3 skipped` 로 끝났다 — 셈이 하나 모자란다.
**이번에도 이름을 잡지 못했다.** 요약을 `tests` 와 `pass` 만 grep 하고 있어서 `fail` 줄이
출력에 없었다. 1차의 교훈을 반만 적용한 것이다: 출력은 남겼지만 **성공한 실행의 출력을**
남겼고, 실패한 그 실행은 다시 부를 수 없었다.

**직후 10회 재현 실패.** 그 뒤 2026-09-02 에 14회 더(부하 아래 6회 포함) — 누적 **55회 중 2회.**

| | 1차 | 2차 |
|:--|:--|:--|
| 언제 | 2026-08-31 오전 | 같은 날, `#24` 머지 직후 |
| 셈 | 1084 pass / 1 fail | 1092 pass / 1 미상 |
| 총 테스트 | 1088 | 1096 |
| 직전에 한 일 | `gate P2 --recheck`(내부에서 전체 스위트를 돌린다) | 문서 grep 몇 개 |
| 이름 | 못 잡음 | 못 잡음 |

🔑 **공통점은 하나뿐이다: 정확히 한 건.** 1096개 중 하나가 통과도 스킵도 아닌 상태로
끝났다. 그것이 실패인지 취소인지도 구별하지 못했다 — 그 구별이 다음 관찰에서 가장 먼저
필요한 값이다.

**손댄 것 (2차).** 시간에 기대는 자리를 찾다가 별개의 잠재 결함을 발견해 고쳤다:
`test/http/portal-names.test.ts` 의 하위 프로세스 마감이 **러너의 마감과 정확히 같았다**
(둘 다 120초). 발화하면 먼저 시작한 러너가 이기고, 그러면 그 테스트가 쓰려던 진단 대신
**취소된 테스트**가 남는다 — 취소는 이유를 말하지 않는다. 90초로 내리고
`test/scripts/test-deadlines.test.ts` 가 그 규칙(테스트의 마감 < 러너의 마감)을 강제한다.

⚠️ **이것이 원인이라고 주장하지 않는다.** 그 파일의 실제 소요는 0.5초라 발화한 적이 없다.
발화하는 날 무엇이 이길지가 정해져 있었을 뿐이고, 지는 쪽이 이유를 아는 쪽이었다.

### 🔴 정정 2026-09-02 — 두 관찰은 **둘 다 로컬**이었다

1·2차를 적을 때 「CI 가 재발의 첫 신호를 준다」고 썼다. **그것이 틀렸다.**

| | 어디서 |
|:--|:--|
| 1차 · 2차 관찰 | **로컬** — Darwin arm64 · Node 26 |
| `flake-watch` (처음 판) | ubuntu-latest · Node 26 |
| CI 의 `check` 실패 이력 | main 최근 20회 중 1회 — 그것은 `#21` 의 `assertOrder` 환경 의존이고 이 관찰이 아니다 |

**CI 는 이 증상을 한 번도 보지 못했다.** 그런데 사냥은 CI 에, 그것도 관찰된 적 없는
운영체제에 붙여 두었다 — 없던 자리를 뒤지는 셈이다.

`flake-watch` 를 세 다리로 고쳤다: **`macos-latest` · Node 26**(관찰된 환경),
`ubuntu-latest` · Node 24(아직 아무도 보지 않은 축), `ubuntu-latest` · Node 26(개발이 서
있는 곳). 세 다리가 갈리면 **그 갈림이 곧 단서다.**

그리고 `check.yml` 에 `workflow_dispatch` 를 붙였다 — 간헐을 좇는 중이라면 다음 주기 실행은
너무 멀다. `gh workflow run check.yml` 로 지금 부를 수 있다.

📌 **왜 처음에 CI 로 갔나.** 「간헐은 판정이 코드 없이 바뀌는 종류이고, 주기 실행이 그것을
재는 자리다」는 맞는 말이었다. 다만 **관찰이 난 환경을 먼저 보지 않았다** — 맞는 이유로 틀린
장소를 골랐다.

### 이번에는 반복 실행을 붙였다

1차에 「관측 1건으로 CI 시간을 태우지 않는다, 두 번째가 생기면 그때 다시 판단」이라고
적었다. 두 번째가 생겼다. 다만 PR 마다 태우지는 않는다 — `check.yml` 의 **주기 실행에만**
붙는다(`github.event_name == 'schedule'`). PR 은 그 잡을 건너뛰고, 건너뛴 잡은 `gate` 가
통과로 읽는다.

주기 실행을 고른 이유는 그것이 이미 「코드가 그대로여도 판정이 바뀐다」를 재려고 있는
자리이기 때문이다. 간헐은 정확히 그 종류다.

## 열림 · 2026-08-31 (1차) · 이름을 잡지 못한 1건

**증상.** `pnpm test` 가 `1084 pass / 1 fail` 로 끝났다. 실패한 테스트의 이름을 잡지 못했다 —
요약만 보고 상세 출력을 버렸다. **그것이 이 기록의 가장 큰 구멍이다.**

**재현 시도 31회, 전부 통과.**

| 조건 | 실행 | 실패 |
|:--|:--|:--|
| 평소 실행 | 11 | 0 |
| `--test-concurrency=16` (CPU 10) | 6 | 0 |
| `gate P2 --recheck` 직후 (관찰 당시와 같은 순서) | 3 | 0 |
| 두 스위트 겹쳐 실행 (2초 간격) | 3 라운드 × 2 | 0 |
| 세 스위트 동시 실행 (지연 없이) | 2 라운드 × 3 | 0 |

**배제된 가설 셋** — 전부 실측으로 배제했다.

| 가설 | 무엇을 재었나 | 결과 |
|:--|:--|:--|
| 인프로세스 환경 오염 | `#17` 은 **스폰된** 프로세스만 격리했으니 인프로세스 `readConfig` 가 셸의 `PARALLAX_STATE_FILE` 을 읽을 수 있다 | 테스트의 모든 `readConfig` 호출이 **명시적 env 객체**를 넘긴다. `data/` 도 비어 있어 실제 상태 파일을 건드린 테스트가 없다 |
| 측정 방법의 산물 | `gate P2 --recheck` 가 내부에서 `pnpm test` 를 돌리므로 두 스위트가 겹쳤을 수 있다 | 같은 순서 3회 재현 실패 |
| 포트 경합 | 포트를 바인드하는 테스트 파일이 38개다 | 겹쳐 실행 5라운드 재현 실패 |

**손댄 것.** 세 번째 가설을 좇다가 **재현과 무관하게 실재하는 경합**을 찾아 고쳤다 —
`freePort()` 가 다섯 벌 복제돼 있었고 그중 하나(`test/dns/server.test.ts`)만 재시도와 UDP
재확인을 갖추고 있었다. `test/support/ports.ts` 로 합치고 별도 프로세스용 재시도를 붙였다.

⚠️ **그것이 이 관찰의 원인이라고 주장하지 않는다.** 증명하지 못했다. 만들어 내는 증상의
종류가 같은 부류일 뿐이고 — 일회성, 부하 상관, 조용할 때 재현 안 됨 — 그 자체로 고칠 값이
있어서 고쳤다.

**보지 못한 축 하나.** CI 는 Node **24 와 26** 을 돌고, 위 31회는 전부 **26**(로컬 v26.4.0)
이다. 24 전용이면 여기서는 절대 보이지 않는다.

### 재발하면 무엇을 할 것인가

1. **출력을 버리지 말 것 — 그리고 요약만 grep 하지 말 것.** 2차에서 `tests` 와 `pass` 만
   추려서 `fail` 줄이 출력에 없었다. `pnpm test 2>&1 | tee /tmp/px-test.log` 로 통째로 남기고
   `fail` · `cancelled` 두 줄을 함께 볼 것 — **실패인지 취소인지가 지금 가장 필요한 값이다.**
   취소면 마감 경합(테스트의 마감 vs 러너의 마감)이고, 실패면 단언이다. 둘은 다른 문제다.
2. 어느 **Node 버전**이었는지 적을 것. 위 표의 빈칸이 그것이다.
3. 그 테스트 파일만 반복 실행 → 격리되면 그 파일의 문제, 안 되면 상호작용이다.
4. 이 절에 한 줄 더 붙일 것. 두 번째 관찰이 있으면 그 둘의 공통점이 곧 답이다.

### 왜 CI 에 반복 실행 잡을 붙이지 않았나 (1차 시점의 판단)

관측 1건으로 주기 반복 실행을 붙이면 CI 시간을 영구히 태우면서 정보는 거의 없다. `test:ci`
가 이미 이름을 남기므로, 재발의 첫 신호는 그쪽에서 온다. **두 번째 관찰이 생기면 그때
다시 판단할 것** — 그때는 「간헐이 있다」가 아니라 「간헐이 반복된다」가 근거가 된다.

✅ **그 조건이 같은 날 충족됐다.** 위 2차 절을 볼 것 — 주기 실행에만 붙였다.
