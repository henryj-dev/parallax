## 0. 이 계획의 규칙

1. **한 항목 = 한 커밋.** 되돌릴 단위가 곧 판단 단위다.
2. **회귀 테스트 없이 닫지 않는다.** 지금 1,021개가 통과하는데 §추가 1·2 가 그
   아래에 있었다.
3. **「점검했다」는 산출물이 있을 때만 적는다.** §4단계는 읽고 끝내는 일이 아니라
   **결과를 남기는 일**이다. 결과가 없으면 그 축은 여전히 미점검이다.
4. **결정이 먼저인 항목은 그렇게 표시했다.** A1 과 D-A2 는 이전 리포트에서 이미
   사람이 판단해 보류·이관한 것이라, 코드를 먼저 쓰면 그 결정을 조용히 뒤집는다.
5. **정정으로 격하된 것은 격하된 자리에서 한다.** §정정 3(인증 실패 제한)은 보안
   수정이 아니라 관측성 항목이고, 그 크기로만 잡는다.

크기 표기: **XS** 한 줄~다섯 줄 · **S** 한 함수 · **M** 한 모듈 · **L** 설계가 필요.

## 2. 1단계 — 쿠키 두 건

### A1 · 🔴 세션 쿠키가 bearer 토큰 **원문**을 담는다 — `L` · **결정이 먼저**

> 근거: §추가 1. 2026-08-22 리포트 **L6** 의 나머지 절반이며 `docs/todo.md`
> 「여전히 남은 것」에 열린 채로 있다.

- **어디:** `src/security/http-authorization.ts:321`(발급) · `:327`
  (`sessionCookieValue`) · `:296`(DELETE) · `:495`(읽는 쪽)
- **지금 무엇이:** `POST /api/v1/session` 이 본문으로 받은 토큰 **그 자체**를
  `parallax_session=` 에 넣는다. 그래서 (a) 쿠키 유출 = 장기 API 자격증명 유출이고,
  (b) `DELETE` 는 쿠키만 지울 뿐 **토큰을 폐기하지 않는다** — 로그아웃이 자격증명을
  회수하지 않는다.
- **변경 후보 — 어느 쪽인지가 D-A1 이다:**

  | | 무엇 | 크기 | 걸리는 것 |
  | --- | --- | --- | --- |
  | ㉠ | 서명된 자체 포함 세션(`signSession`)을 토큰 경로에도 발급 | S~M | **비밀키 출처가 없다.** `sessionSecret` 은 지금 `PARALLAX_OIDC_SESSION_SECRET` 뿐(`src/config.ts:414`)이라 OIDC 를 안 쓰는 배포에는 존재하지 않는다. 새 환경변수가 필요하고, 부팅마다 난수로 만들면 재시작에 전원 로그아웃 + 다중 replica 가 서로의 쿠키를 거부한다 |
  | ㉡ | 서버측 세션 저장 + 쿠키에는 세션 id 만 | M~L | 서빙 런타임에 리포지터리를 주지 않는다(`exposeStores`). 저장소를 새로 열어야 하고, 그 결정은 D3 이 이미 반대편으로 내려 놨다 |
  | ㉢ | 토큰 digest 를 쿠키에 넣고 검증 시 digest 로 대조 | S | 재사용 불가는 산다. **폐기는 못 산다** — 여전히 토큰 수명에 묶인다 |

  📌 **㉠ 이 기본값이다.** ㉢ 은 (a) 만 사고 (b) 를 못 사는데, 재검증이 무겁게 본
  것은 (b) 쪽이다.
- **완료 정의:**
  1. `POST /api/v1/session` 이 돌려준 쿠키 값을 그대로 `Authorization: Bearer` 로
     보내면 **401** 이다.
  2. `DELETE /api/v1/session` 뒤에 **같은 쿠키 값을 다시 제시하면 401** 이다.
     지금은 브라우저에서 지워질 뿐이라, 값을 복사해 둔 사람에게는 아무 일도 안 난다.
- **회귀 테스트:** 위 둘을 그대로. **둘째가 이 항목의 본체다** — 첫째만 있으면 ㉢
  으로도 통과한다.
- ⚠️ **읽는 쪽의 `TOKEN_PATTERN`**(`:514` · `:529`)이 새 쿠키 값 모양을 통과시키는지
  먼저 볼 것. `signSession` 은 `v1.<b64url>.<b64url>` 이라 점이 알파벳에 있어 **지금도
  통과한다 — 통과하는 게 함정이다.** 토큰과 세션값을 같은 검증기로 보면 둘을 구별하지
  못하고, 완료 정의 1 이 요구하는 것이 정확히 그 구별이다.
- ⚠️ 포털은 이 쿠키를 **읽지 않는다**(HttpOnly, `public/api-client.js:26`). 그래서 이
  변경의 파급은 서버 안에 갇힌다 — 확인했고, 그게 이 항목을 생각보다 값싸게 만든다.

### A2 · 세션 쿠키에 `__Host-` 접두사가 없다 — `S`

> 근거: §추가 2. 핸드셰이크 쿠키에는 이미 있고(`src/http/identity-routes.ts:169`),
> 그 자리 주석이 **왜 그 절반이 예방이고 나머지 절반은 사후인지** 적어 놨다.

- **어디:** 발급 — `src/http/identity-routes.ts:115`(`parallax_identity`) ·
  `:118`(`parallax_oidc_id`) · `src/security/http-authorization.ts:327`
  (`parallax_session`). 삭제 — `identity-routes.ts:131` ·
  `http-authorization.ts:337`(`clearedCookieValue`). 읽기 — `:495` · `:507` ·
  `identity-routes.ts:130`.
- **변경:** `handshakeName()` 과 **똑같은 조건부**(https 일 때만 `__Host-`)를 저 셋과
  그 삭제 쿠키에 적용한다. **읽는 쪽도 같은 함수로 이름을 만들어야 한다** — 한쪽만
  바꾸면 로그인이 성립하지 않는다.
- **완료 정의:** https 요청에서 세 쿠키가 전부 `__Host-` 로 나가고, `Domain=` 붙은
  동명 쿠키를 브라우저가 애초에 받지 않는다. plain-HTTP loopback 에서는 지금 이름 그대로.
- **회귀 테스트:**
  - https `Request` 로 발급 → `set-cookie` 세 줄 전부 `__Host-` + `Secure` + `Path=/`
    + `Domain` 없음
  - http `Request` 로 발급 → 접두사 없음(그리고 `Secure` 없음)
  - 발급한 쿠키로 인증이 성립한다 — 읽는 쪽 이름이 따라갔는지
  - **삭제 쿠키도 같은 이름으로 나간다** — 이름이 어긋나면 로그아웃이 아무것도 안 지운다
- ⚠️ **`cookieName` 은 설정 가능하다**(`http-authorization.ts:446`,
  `COOKIE_NAME_PATTERN`). `_` 와 `-` 는 패턴 알파벳에 있어 접두사를 붙여도 통과하지만,
  **설정값이 이미 `__Host-` 로 시작하는 경우** 이중 접두사가 되지 않게 할 것.
- ⚠️ **이 변경은 배포 시점에 전원을 한 번 로그아웃시킨다.** 브라우저에 남은 옛 이름
  쿠키를 계속 받아 주면 shadowing 이 그대로 열려 있으므로 **받아 주지 않는 쪽이
  맞다.** 릴리스 노트에 적을 것.
- 🔑 **A1 보다 값이 싸고 A1 과 독립이다.** A1 의 결정이 늦어지면 이것부터 한다.

## 3. 2단계 — OIDC

### A3 · ID token 검증과 `sub` 대조 — `M`

> 근거: §정정 2. **본문 권고 1 을 축소하는 것이 아니라 나눈 것이다.** `nonce` 는
> 애초에 발행되지 않아 검증 대상이 아니고(→ A4), 나머지는 여전히 해야 한다.

- **어디:** `src/security/oidc.ts:201`(`exchangeCode`) · `:244`(`readIdentity`) ·
  호출부 `src/http/identity-routes.ts:109-110`
- **변경:**
  1. `exchangeCode` 가 받은 `id_token` 의 `iss` · `aud` · `exp` 를 검증한다. `iss` 는
     discovery 가 자기 것이라 주장한 값(`oidc.ts:96` 이 이미 그 자기주장을 검사한다)과,
     `aud` 는 `config.clientId` 와 대조한다.
  2. **UserInfo 의 `sub` 가 ID token 의 `sub` 와 같은지 대조한다.** OIDC Core §5.3.2
     의 **MUST** 이고, 지금 `readIdentity` 는 userinfo 의 `sub` 만 읽는다.
  3. `id_token` 이 없을 때 어떻게 할지 정한다 — 지금은 **없어도 통과**한다
     (`oidc.ts` 의 `idToken` 이 optional). 필수로 만들 것인지가 이 항목의 유일한
     설계 판단이다.
- **완료 정의:** 위 셋이 각각 틀린 값을 받았을 때 로그인이 `OidcError` 로 실패한다.
- **회귀 테스트** (전부 가짜 `fetchImpl` 로):
  - `aud` 가 다른 ID token → 거부
  - `iss` 가 discovery 의 issuer 와 다른 ID token → 거부
  - 이미 만료된 `exp` → 거부
  - **ID token 의 `sub` ≠ userinfo 의 `sub` → 거부** ← 이 항목의 본체
  - 전부 맞는 경우 → 지금과 동일하게 통과(역할 매핑도 그대로)
- 📌 **서명 검증(JWKS)은 이 항목에 넣지 않는다.** OIDC Core §3.1.3.7 이 token
  endpoint 에서 TLS 로 직접 받은 ID token 은 서명 검증을 TLS 서버 검증으로 갈음할 수
  있다고 적고 있고 `exchangeCode` 가 정확히 그 경우다. **다만 그 예외가
  `iss`·`aud`·`exp` 까지 면제해 주지는 않는다** — 그래서 위 셋은 남는다. JWKS 는
  별건으로 둔다.

### A4 · `nonce` — **발행이 먼저다** — `S` · A3 뒤

- **어디:** `src/security/oidc.ts:184`(`beginAuthorization`) · 콜백
  `src/http/identity-routes.ts:95-110`
- **지금 무엇이:** 인가 요청 파라미터는 `response_type` · `client_id` ·
  `redirect_uri` · `scope` · `state` · `code_challenge` · `code_challenge_method`
  뿐이고 `grep -n nonce src/security/oidc.ts` 는 **0건**이다.
- **변경:** 인가 요청에 `nonce` 를 넣고 `state`·`verifier` 와 같은 방식으로 핸드셰이크
  쿠키에 보관했다가, 콜백에서 ID token 의 `nonce` 와 대조한다.
- **완료 정의:** 저 grep 이 0건이 아니게 되고, 값이 다른 `nonce` 를 든 ID token 이
  거부된다.
- **회귀 테스트:** 다른 `nonce` → 거부. `nonce` 없는 ID token → 거부.
- ⚠️ **A3 없이 이것만 하면 아무것도 사지 못한다** — 대조할 자리가 없다. 이 계획에서
  강제 순서가 있는 유일한 쌍이다.
- ⚠️ 핸드셰이크 쿠키가 하나 늘어난다. **A2 의 이름 규칙을 그대로 따를 것.**

### A5 · DNS forwarding 을 **upstream 별·사유별**로 기록 — `S`

> 근거: §정정 5. **근거를 「간헐 실패」가 아니라 「관측 불가」에 둔다** — 같은 커밋의

- **어디:** `src/dns/server.ts:1261`(`forward`). 세 갈래 `continue`(DNS 해석 실패 ·
  주소 거부 · 남은 예산 소진)와 relay 실패가 **전부 같은 침묵**으로 떨어진다. 지금
  남는 것은 `dnsForwardSeconds` 의 `outcome: answered|failed` 둘뿐이다(`:367`).
- **변경:** 실패 사유를 나눈다 — `resolve` · `address_refused` · `budget` ·
  `connect_send` · `correlation` · `timeout`. 실패 전용 카운터를
  `src/observability/signals.ts` 에 기존 것들과 같은 형태로 둔다.
- ⚠️ **라벨에 호스트 이름·질의 이름을 넣지 말 것.** `signals.ts:75-82` 가 라벨 집합을
  작고 고정되게 유지하는 이유를 적어 놨다. upstream 은 설정된 목록이라 고정 집합이긴
  하지만, **인덱스로 넣을지 값으로 넣을지는 정하고 갈 것.**
- **완료 정의:** 위 여섯 갈래가 각각 다른 값으로 관측된다.
- **회귀 테스트:** 가짜 `resolveHost` 와 가짜 relay 로 여섯 갈래를 하나씩 만들고
  `render()` 출력에서 해당 라벨이 1 인지 본다. `resetMetrics()` 를 쓰는 기존 테스트와
  같은 방식.

- **변경:** 코드 변경 없음. `docs/todo.md` 의 해당 줄과 배포 문서에 **「replica 를
  넘나드는 실패를 한자리에서 보고 싶으면 공용 저장소가 필요하다 — 우회 차단이 아니라

- **완료 정의:** 다음 검수가 이 항목을 다시 취약점으로 올릴 때 반박할 줄이 있다.

## 5. 4단계 — 아무도 안 본 일곱 축

> 근거: §추가 5 · §추가 7 · §정정 6. **§점검 개요는 대상에 "실행 스크립트, 설정
> 코드" 를 넣었는데 본문의 언급 횟수가 0회다.** 이 단계는 그 간격을 닫는다.

각 항목의 **완료 정의는 공통이다: 이 파일 §부록 A 에 「무엇을 봤고 무엇이 나왔나」를
한 문단 이상 적는다.** 아무것도 안 나왔으면 "아무것도 나오지 않았다" 를 적는다 —
그게 미점검과 점검을 가르는 유일한 표시다.

- **A7 · `pnpm audit`** — 원 점검에서 **네트워크 차단으로 실행 불가**였고 그 한정이
  §검증 결과 안쪽에만 있어 **결론이 의존성까지 덮는 것처럼 읽혔다**(§정정 6).
  네트워크가 되는 자리에서 `pnpm run audit`(= `--audit-level moderate`)를 돌리고
  결과를 적는다. 프로덕션 의존성은 `pg` 하나뿐이라 결과는 짧을 것이다 — **짧은 것과
  없는 것은 다르다.**
- **A8 · `migrations/`** — 5개 `.sql`, 특히 `004_security_invariants.sql` 과
  `005_access_token_lifetime.sql`. 볼 것: 불변식이 실제로 제약으로 걸려 있는가,
  재실행 안전한가, 앞 버전에서 올라오는 경로가 있는가.
- **A9 · `Dockerfile`** — 이미지 빌드와 **uid·권한**. CI 의 `docker` 잡이 이 질문에
  답하고 있으니 **그 잡이 무엇을 주장하는지부터 읽을 것.**
- **A10 · `.github/workflows/**`** — 다섯(`check` · `scripts` · `docker` · `codeql` ·
  `dependency-review`). 볼 것: `permissions:` 범위, `pull_request_target` 사용 여부,
  서드파티 액션 핀 방식, 포크 PR 에 시크릿이 닿는 경로.
- **A11 · `scripts/claude-hooks/**` · `scripts/git-hooks/**`** — CI(`scripts.yml`)에서
  **실제로 도는** 파이썬 스위트와 shellcheck. ⚠️ **이것은 stardust 의 스냅샷이다**
  (`CLAUDE.md` 참조). 여기서 결함을 찾으면 **고칠 자리는 stardust 이고 여기로 다시
  뜨는 것**이지, 여기서 고치는 것이 아니다 — 여기서 고치면 다음 스냅샷이 덮는다.
- **A12 · 포털 브라우저 실조작** — `public/**` 는 아직 정적 읽기와 `tsc --checkJs`
  뿐이다(`docs/todo.md` 「여전히 남은 것」). §포털 XSS 의 **결론은 재검증에서 유지
  됐다** — 바뀌는 것은 결론이 아니라 **그 결론이 정적 읽기로 내려졌다는 표시**다.
  실조작으로 볼 것: 저장된 존/레코드/토큰 subject 에 `<img src=x onerror=…>` 를 넣고
  목록·상세·감사 뷰에서 실행되지 않는지, `signin_error` 가 `setLiveMessage` 의
  `textContent` 로만 들어가는지(`public/app.js:64`).
- **A13 · `verify:cloudflare`** — 실제 Cloudflare 자격증명이 필요하다. 없으면
  **「자격증명이 없어 못 돌렸다」를 적는다** — 상태는 지금과 같지만, 다음 사람이 같은
  것을 다시 발견하지 않는다.

  OIDC 비밀키를 재사용할지**, 그리고 다중 replica 를 전제로 할지.

  그쪽은 보류 결정이 유효하고, 재검증도 그것을 뒤집을 새 근거를 대지 못했다.
